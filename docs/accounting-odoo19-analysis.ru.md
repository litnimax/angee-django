# Accounting arpee → Angee: анализ по онтологии Odoo 19

Дата исследования: 2026-09-05. Статус: анализ исходников и проект реализации; функциональные изменения не выполнены.

## 1. Вывод

В arpee уже реализован начальный бухгалтерский контур, а не только CRUD счетов: общая проводка, ее строки, специализация Invoice, налоги, платежи, частичная сверка, нумерация и аналитические записи. Продолжать следует от этого контура, сохраняя предметные отношения Odoo и используя собственные механизмы Django/Angee.

Однако баланс дебета и кредита сам по себе не гарантирует правильность учета. Сейчас возможны неверная сумма повторного платежа, неверное направление возврата, неполная обработка графа сверки и неверное извлечение нескольких включенных налогов. Эти проблемы важнее добавления новых экранов.

Odoo здесь — источник бизнес-понятий, инвариантов и сценариев. Это не предложение подключать Odoo как runtime, воспроизводить его ORM или переносить все его возможности одним изменением.

## 3. Бизнес-онтология

| Понятие и отношение | Odoo 19 | arpee сейчас | Решение для развития |
|---|---|---|---|
| Компания владеет книгой учета и валютой | `res.company` | `arp.Company` + `CompanyAccounting` | Сохранить владельца; добавить учетную политику и закрытие периодов |
| Контрагент участвует в обязательстве | `res.partner` | `parties.Party` | Расширять существующего Party, в том числе company-specific настройками счетов |
| Счет классифицирует движение | `account.account` | `Account`, 9 видов, уникальность company/code | Дополнить классификацию по требованиям отчетов; запретить недопустимые счета при posting |
| Журнал определяет книгу операций | `account.journal` | `Journal`, 5 видов | Проверять назначение, компанию, счета и серии |
| Проводка содержит строки | `account.move` → `account.move.line` | `JournalEntry` → `JournalItem` | Единый ledger остается источником бухгалтерских сумм |
| Invoice — специализация проводки | `move_type` | Материализованный child `Invoice` | Сохранить естественный Angee child, не вводить вторую независимую бухгалтерскую запись |
| Долг имеет сумму и срок | Строки receivable/payable с `date_maturity` | Одна counterpart-строка; `due_date` на документе | Материализовать график платежей отдельными строками задолженности |
| Погашение связывает противоположные долги | `account.partial.reconcile` | `PartialReconcile` | Размер погашения и остаток — факты графа, а не ручной статус счета |
| Полная сверка замыкает компоненту графа | `account.full.reconcile` | `FullReconcile`, только текущие settled items | Обрабатывать все связанные строки и partials |
| Платеж фиксирует получение/выдачу денег | `account.payment`, отдельные payment_type и partner_type | `Payment.direction`, проводка bank/counterpart | Разделить направление денег и тип контрагента |
| Выписка подтверждает банковское движение | Statement / statement line | Нет моделей | Отдельный объект и процесс банковской сверки |
| Налог преобразует базу и создает учетные последствия | Tax + repartition + tags + fiscal position | Percent/fixed, invoice/refund distributions | Общий результат расчета базы, налогов, распределений; затем materialization в GL |
| Аналитика распределяет экономический результат | `analytic` + account bridges | `arp.analytic`, distribution на item | Сохранить отдельный addon и связь с первичной строкой |
| Отчет — проекция проводок на дату | Report/line/expression/column | Нет бухгалтерских отчетов | Начать с проверяемых GL, оборотов, задолженности, BS/P&L |

Типовой процесс: документ → валидация → posting → строки доходов/расходов, налогов и задолженности → платеж → partial reconciliation → остаток → банковское подтверждение → отчет на выбранную дату. Возврат и исправление создают связанные обратные документы; закрытие периода ограничивает изменения.

Для Odoo сроки оплаты действительно создают отдельную journal item на каждую дату, что существенно для aging и частичной оплаты: [официальная документация payment terms](https://www.odoo.com/documentation/19.0/applications/finance/accounting/customer_invoices/payment_terms.html).

Особенность именно Odoo 19: платеж не обязан создавать проводку. Это зависит от настройки outstanding accounts; регистрация платежа и банковское подтверждение — разные события. Нельзя объявлять текущую схему arpee «всегда сразу по банку» полным соответствием Odoo. См. [Payments](https://www.odoo.com/documentation/19.0/applications/finance/accounting/payments.html) и [Journals](https://www.odoo.com/documentation/19.0/applications/finance/accounting/get_started/journals.html).

## 4. Что уже стоит сохранить

- `JournalEntry.post()` централизует materialization, баланс, аналитику и номер; Invoice переопределяет предметные hooks. Источник: `addons/arp/accounting/models.py:695,958`.
- Деньги используют `MoneyField`, валюту и округление из `angee.money`; нумерация — `angee.sequence`. В целевом Angee уже есть курсы и конвертация, но posting arpee намеренно отклоняет чужую валюту (`models.py:760`).
- `StateTransitions` и `save_state` уже существуют. В целевом Angee `save_state` повторно проверяет persisted state под блокировкой; утверждать, что защиты от повторного перехода вообще нет, неверно. Атомарность всей операции остается обязанностью вызывающего бизнес-метода/транзакции.
- Сверка блокирует выбранные строки по pk и вычисляет остатки после блокировки (`models.py:1131`). Это хорошая основа, которую нужно расширить до корректной обработки связанной компоненты.
- Аналитика выделена в отдельный addon. Sales/purchase создают документы через `InvoiceManager.create_document`, а свои ссылки добавляют через extensions; accounting не импортирует sales/purchase.
- UI использует общие List/Form/Record primitives. Существуют страницы invoices, bills, payments, entries и настроек. GL-ресурсы в GraphQL сейчас read-only; полноценного ввода ручной проводки через этот API нет (`schema.py:432`).
- Тесты уже проверяют простой posting, запрет обычного редактирования posted item, foreign currency rejection, reversal, refund distributions, округление, изоляцию чтения и конкурентную выдачу номеров. Это полезная база, но не покрытие всего расчетного жизненного цикла.

## 5. Дефекты и риски с конкретными сценариями

Приоритет P0 — исправить до использования контура как достоверной книги учета. «Подтверждено по коду» означает непосредственно наблюдаемое правило/отсутствие необходимой ветки; доступность конкретного обхода через composed API отдельно требует runtime-проверки.

| Приоритет | Наблюдение и последствия | Доказательство / приемочный сценарий |
|---|---|---|
| P0 | Платеж по умолчанию равен сумме исходных totals, а не текущих остатков | `PaymentManager.register`, `models.py:1501–1503`. Счет 100, оплачено 40: второй платеж без amount должен быть 60, сейчас вычисляется 100 |
| P0 | Customer refund трактуется как inbound; vendor refund — как outbound | `inbound = first.kind in _RECEIVABLE_KINDS`, `models.py:1502`; множество включает customer refund. `_build_entry:1617` дополнительно выводит counterpart из направления. Нужны независимые оси customer/vendor и receive/send |
| P0 | Нет полноценной валидации платежной группы | `schema.py:624`, `models.py:1481`. Пустой список доходит до `invoices[0]`; нет явного разбиения/отказа для разных компаний, валют, контрагентов и семантики документов. Доступ к двум компаниям не разрешает смешивать их учет |
| P0 | Отсутствующий банковский счет подменяется receivable | `models.py:1625`. Платеж может дать D receivable / C receivable вместо движения денег. Отсутствие корректной конфигурации должно блокировать posting |
| P0 | Полная сверка не охватывает исторически связанные строки | `_stamp_full_reconciles`, `models.py:1215`. При счете 100 и платежах 40+60 последний вызов видит счет и платеж 60, но не платеж 40. Нужна одна корректно закрытая связанная компонента, а не маркер на текущем подмножестве |
| P0 | Unreconcile пересчитывает только переданные строки | `models.py:1173`. Удаление partial по payment item меняет также остаток invoice item, но invoice может сохранить `paid`; у непереданных строк возможны устаревшие `reconciled` после удаления FullReconcile. Пересчитать и заблокировать затронутые концы/компоненты |
| P0 | Защита posted ledger не замкнута на все пути записи | `JournalItem.save:1377` защищает существующие строки при save. Нет предметного запрета delete в моделях, изменения шапки/Payment после posting; Invoice/Payment write backends не задают `delete_guard` (`schema.py:481,507`). `entry` у item — CASCADE. Подтвержден пробел в доменных guards; проверить через API delete/update, M2M, nested writes и bulk operations с реальными правами |
| P0 | Достаточность проверки posting не доказана: баланс допускает пустой набор | `assert_balanced:747` сравнивает только суммы. Нет здесь обязательной проверки наличия строк, счетов, контрагента, согласованности journal/account/tax/company. `account` nullable; zero-zero проверяется в `clean` только когда parent уже posted. Проверять весь агрегат перед сменой состояния, включая внутренние системные записи |
| P1 | Несколько включенных налогов извлекаются неверно | `Invoice._materialize_document_lines:983`, `tax.py`. Для gross 120 с двумя независимыми включенными 10% на одной базе фактические стратегии дают net 99.17 и total 119.01 вместо 100 и 120. Изолированно воспроизведено Python 3 через текущий `PercentTaxCompute` |
| P1 | Сроки платежа не создают график долга | `PaymentTerm.compute_due:492`, `Invoice._materialize_counterpart:1075`. Из графика сохраняется только последняя дата; нет `date_maturity` на item. Счет 1000 с 30/70 должен дать долги 300 и 700 на разные даты |
| P1 | Распределения налогов не валидируют ожидаемую структуру | `_materialize_tax_group:1025` остаток кладется в первое распределение; отсутствие распределений ведет к default account журнала. Нельзя таким остатком маскировать ошибочную сумму процентов. Нужны явные правила base/tax lines, tax tags и допустимых факторов |
| P1 | Серии не заменяют целостность номеров документов | `JournalEntry.number:634` не имеет constraint уникальности, `post(number=...)` допускает явный номер. Нужна предметная уникальность в согласованной области и неизменность уже выданного номера; учитывать, что Payment и его entry намеренно используют один номер |
| P1 | Reopen не содержит очистки зависимых учетных фактов | `reopen:724` пустой; `_generate_analytic_lines:780` создает строки заново. При включении policy возможны дубли аналитики, проблемы со сверкой и новый номер при repost. По умолчанию reopen отключен; включать только после реализации полного протокола |

Отдельно проверить создание Invoice через общий GraphQL: обязательный `JournalEntry.date` не включен в writable-поля Invoice, а create_document и demo-фабрики передают его явно. Нужно подтвердить фактическую defaulting-цепочку в runtime; по декларации API она не очевидна.

Сверка сейчас проверяет один счет, одну валюту и posted status. Она не устанавливает полноценную семантику платежной группы. Исправление должно жить в модели/manager, чтобы одинаково работать из API, jobs, импортов и внутренних вызовов.

## 7. Архитектура реализации и место изменений

Owner map по действующему `AGENTS.md` целевого checkout:

| Владелец | Ответственность |
|---|---|
| Django/PostgreSQL | Decimal storage, транзакции, блокировки, FK/Check/Unique constraints; migrations |
| `angee.base.transitions` | Общая механика разрешенных переходов и конкурентного сохранения состояния |
| `angee.money` | Валюты, курсы, базовое округление/конвертация; фискальная политика задается потребителем |
| `angee.sequence` | Выдача номера под транзакцией; accounting определяет scope, серию и бизнес-уникальность |
| `arp.base` / `arp.Company` | Компания и membership; accounting расширяет ее учетными настройками |
| `arp.accounting` | Проводки, posting, налоги, задолженность, платежи, reconciliation, locks и бухгалтерские отчеты |
| `arp.analytic` | Планы/счета/распределения аналитики; accounting добавляет происхождение из JournalItem |
| GraphQL / React | Тонкие вызовы предметных операций и отображение через существующие primitives |

Analog inventory: для специализации модели — существующий `parties.Person` и текущий Invoice; для cross-addon связей — sales и purchase extensions; для общих примитивов — money и sequence; для UI — существующие accounting ConfigPages/InvoiceWorkbench и shared List/Form. Новое бухгалтерское понятие не должно попадать в framework core только потому, что оно сложно.

В указанном angee-django нет `arp.accounting` и `arp.base`. Поэтому все бизнес-изменения нельзя корректно внести только в этот checkout без изменения состава репозитория. Рекомендуемая граница: общие улучшения делать здесь, предметные исправления — в owner `arp.accounting`. Если accounting должен физически поставляться из angee-django, это отдельное структурное решение: переносить согласованную addon-семью вместе с зависимостями, namespace, тестами и планом удаления старого владельца. Простое копирование `models.py` породит двух владельцев и неработающие зависимости.

В этой задаче изменен только настоящий отчет в целевом checkout. Перенос addon-семьи и изменение runtime в анализ не включены.

Ожидаемое упрощение реализации: убрать из Payment вывод типа контрагента через направление, заменить totals на единый остаток; заменить локальное маркирование сверки обходом предметного графа; удалить обходные fallback-счета; при переносе удалить старую реализацию после переключения потребителей. Не создавать параллельные валюты, нумерацию, state machine или таблицы контрагентов.

Старая `specs/domains/accounting.md` в arpee — историческая гипотеза, не текущее устройство: там используется `arp.account` вместо фактического `arp.accounting`, money/sequence/state transitions описаны как отсутствующие, а ledger/tax предлагается поднимать в core. Актуальные код и AGENTS имеют приоритет. Спецификацию нужно согласовать с owner map до реализации.

## 8. Очередность и критерии готовности

1. **Зафиксировать размещение и baseline.** Выбрать способ доставки addon без дублирования владельцев. Собрать host, подключенный именно к проверяемым исходникам; прогнать существующие accounting tests и frontend checks. Сохранить минимальные сценарии с ожидаемыми проводками.
2. **Закрыть P0.** Доменная валидация полного агрегата, draft-only editing/deletion, атомарный posting; остаток и две оси Payment; проверка платежных групп; правильные компоненты reconcile/unreconcile. Приемка: 100→40→60, 40→unreconcile, возврат клиенту/от поставщика, повтор запроса, конкурирующие платежи, отказ при смешении компаний, запрет удаления posted invoice.
3. **Довести задолженность и налоги.** Сроки на строках, округление графика до итоговой суммы, несколько включенных налогов, refund distributions, валидация налоговых счетов. Приемка: 1000→300/700, gross 120→net 100 + 10 + 10; для каждого сценария совпадают документ, GL и residual.
4. **Добавить учетный контроль и базовые отчеты.** Ручные balanced entries, lock dates, номерные constraints, audit/reversal policy, GL/ОСВ/BS/P&L/aging. Приемка: сумма дебетов = сумме кредитов, движение счета сверяется с GL, остаток на прошлую дату учитывает дату погашения, закрытый период не изменяется разрешенными каналами.
5. **Добавить банковский цикл.** Payment methods, outstanding/suspense, statement import и matching, авансы, комиссии. Приемка: факт регистрации и факт банковского подтверждения различимы; повторный импорт не дублирует движение.
6. **Добавить FX.** Компания/операция/погашение в разных валютах, snapshot курса, exchange difference и корректное обратное действие. Сначала полная модель двух валют, затем разрешение foreign-currency posting.
7. **Расширять по выбранному бизнесу.** Локализации, налоговые формы, EDI, PDF, cash basis, advanced reports. Набор зависит от стран, юридических лиц и процессов; полного parity без этих границ заявлять нельзя.

Это порядок зависимостей, не календарная оценка. Минимальные параметры для следующего этапа: где поставляется accounting, страна/режим учета, число компаний, валюты, необходимость банковской сверки и электронных документов. Они не мешают уже сейчас принять результаты анализа и сформировать пакет P0.

## 9. Проверка будущей реализации

- Unit/domain: знаки всех четырех видов invoice/refund, multiple tax, distribution rounding, installments, residual и graph closure.
- PostgreSQL transaction tests: один документ одновременно постят два вызова; два платежа гасят один остаток; reconcile и unreconcile пересекаются; полный rollback не оставляет номера, partials или аналитические строки.
- API/security: обычный бухгалтер, invoicer и пользователь двух компаний; update/delete/M2M/nested writes не обходят posting law; права доступа и совместимость ссылок проверяются раздельно.
- Отчеты: итоговая сверка с GL и историческая дата; документальные totals не подменяют posted ledger; draft/cancelled исключаются согласно политике.
- UI: создание → строки/налоги → posting → partial payment → остаток → refund/reversal; общие формы/таблицы и отображение ошибок.
- Доставка: owner migrations, `angee build`, миграции runtime, permissions/resources/schema; необходимые Python/frontend/browser checks по действующему AGENTS. Генерируемый runtime вручную не править.

Исторические документы при расширении не перепроводить автоматически по новой налоговой формуле. Для введения новых полей и reconciliation semantics нужен отдельный план миграции: инвентаризация, проверка исходных остатков, выявление поврежденных компонентов, заполнение только доказуемых значений и отчет расхождений.
